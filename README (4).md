# User Company Platform

Платформа для роботи з користувачами та компаніями, побудована на .NET і
мікросервісному підході. Проєкт містить окремі сервіси для користувачів
і компаній, а також фоновий сервіс для надсилання сповіщень.

> README підготовлено за наданою структурою проєкту та конфігурацією
> Docker Compose. Перед публікацією перевірте назви змінних середовища й
> фактичні адреси API у `appsettings.json` та `Program.cs`.

## Архітектура

У рішенні є такі основні частини:

-   **UserService.API** --- HTTP API для роботи з користувачами.
-   **UserService.Application** --- прикладна логіка: команди, запити,
    DTO, мапінг і валідація.
-   **UserService.Domain** --- доменні сутності, enum-и та інтерфейси.
-   **UserService.Infrastructure** --- доступ до даних, репозиторії,
    сервіси, JWT та Unit of Work.
-   **CompanyService.API** --- HTTP API для роботи з компаніями.
-   **CompanyService.Application** --- команди й запити для створення,
    оновлення, видалення та отримання компаній, DTO, мапінг і валідація.
-   **CompanyService.Domain** --- сутність `Company` та доменні
    інтерфейси.
-   **CompanyService.Infrastructure** --- `CompanyDbContext`, міграції,
    репозиторій і Unit of Work.
-   **NotificationService.Worker** --- фоновий worker, який обробляє
    запити/події та надсилає сповіщення.
-   **NotificationService.Domain** і
    **NotificationService.Infrastructure** --- доменні контракти та
    інфраструктура сповіщень, зокрема споживачі повідомлень, DbContext,
    репозиторії та сервіси.
-   **Contracts** --- спільні контракти, події та запити, якими
    обмінюються сервіси.

У `Application` використовується поділ на команди й запити (CQRS). У
проєкті також присутні валідація, мапінг, кешування та доступ до даних
через репозиторії/Unit of Work.

## Технології та інфраструктура

За наданою конфігурацією проєкт використовує:

-   C# / .NET;
-   ASP.NET Core Web API;
-   Entity Framework Core та PostgreSQL;
-   RabbitMQ для обміну повідомленнями;
-   Redis для кешування;
-   Docker та Docker Compose для запуску інфраструктури й сервісів;
-   JWT для автентифікації (у UserService).

## База даних: скільки їх і чи вони окремі?

У поточному `docker-compose.yml`, який ви надали:

1.  Створюється **один контейнер PostgreSQL** (`postgres`).
2.  У ньому ініціалізується **одна PostgreSQL-база даних** ---
    `UserService` (`POSTGRES_DB: UserService`).
3.  У змінних середовища `users-service`, `companies-service` і
    `notifications-worker` вказано однаковий рядок підключення з
    `Database=UserService`.

Отже, за цією конфігурацією UserService, CompanyService і Notification
Worker підключаються до **однієї фізичної PostgreSQL-бази
`UserService`**. Це не три незалежні бази даних.

При цьому в коді можуть бути окремі `DbContext` і набори EF Core
migrations для різних сервісів. Це розділяє модель доступу до даних на
рівні коду, але саме по собі **не створює окремих баз даних**.

Інші компоненти:

-   **Redis** --- окреме сховище в пам'яті, яке зазвичай
    використовується для кешу. Це не PostgreSQL-база.
-   **RabbitMQ** --- брокер повідомлень, а не база даних.

Якщо мета --- повна ізоляція даних мікросервісів, зазвичай кожному
сервісу надають власну базу даних (або принаймні окрему логічну БД із
власними обліковими даними та правами). Для цього потрібно змінити
конфігурацію PostgreSQL, connection strings і налаштування міграцій.
Поточний README не стверджує, що така ізоляція вже налаштована.

## Що потрібно для запуску

Встановіть:

-   [Docker Desktop](https://www.docker.com/products/docker-desktop/) із
    запущеним Docker Engine;
-   Git, якщо плануєте клонувати репозиторій;
-   .NET SDK відповідної версії, якщо хочете запускати або збирати
    сервіси без Docker.

Для запуску всього середовища через Docker достатньо Docker Desktop.

## Запуск через Docker Compose

Відкрийте термінал у кореневій папці репозиторію --- там, де
розташований `docker-compose.yml` або `compose.yaml`.

### 1. Перевірте конфігурацію Compose

``` bash
docker compose config
```

Якщо команда завершується без помилок, YAML-конфігурація коректна.

### 2. Зберіть образи та запустіть контейнери

``` bash
docker compose up -d --build
```

Під час першого запуску Docker завантажить базові образи та збере
.NET-сервіси. Це може зайняти кілька хвилин.

### 3. Перевірте стан контейнерів

``` bash
docker compose ps
```

Переглянути всі контейнери, включно із зупиненими:

``` bash
docker compose ps -a
```

### 4. Перегляньте логи

Логи всіх сервісів:

``` bash
docker compose logs -f
```

Логи конкретного сервісу:

``` bash
docker compose logs -f users-service
docker compose logs -f companies-service
docker compose logs -f notifications-worker
```

Щоб вийти з перегляду логів, натисніть `Ctrl+C`. Це не зупиняє
контейнери.

### 5. Зупиніть проєкт

``` bash
docker compose down
```

Ця команда зупиняє та видаляє контейнери й мережу Compose, але не
видаляє іменований том `pgdata`, у якому зберігаються дані PostgreSQL.

> Увага: `docker compose down -v` видаляє також томи, зокрема `pgdata`.
> Це може призвести до втрати даних бази. Використовуйте цю команду лише
> тоді, коли справді хочете очистити дані.

## Порти сервісів

Згідно з наданим Compose-файлом налаштовано такі порти:

  Компонент               Порт хоста Призначення
  --------------------- ------------ ---------------------------------
  UserService API             `5000` HTTP API
  CompanyService API          `5001` HTTP API
  PostgreSQL                  `5432` Підключення до БД
  RabbitMQ                    `5672` AMQP-підключення
  RabbitMQ Management        `15672` Вебінтерфейс керування RabbitMQ
  Redis                       `6379` Підключення до Redis

Адреси API для локального доступу: `http://localhost:5000` та
`http://localhost:5001`, якщо застосунки слухають відповідні порти
всередині контейнерів. Swagger буде доступний лише якщо він увімкнений у
відповідному середовищі та налаштований у коді.

RabbitMQ Management UI: `http://localhost:15672`. У наданому
Compose-файлі задані облікові дані `guest` / `guest`; для реального
розгортання їх потрібно замінити на безпечні.

## Корисні команди Docker

Переглянути запущені контейнери:

``` bash
docker ps
```

Переглянути всі контейнери:

``` bash
docker ps -a
```

Перезапустити сервіси:

``` bash
docker compose restart
```

Перебудувати й перезапустити:

``` bash
docker compose up -d --build
```

Переглянути використання логів конкретного сервісу:

``` bash
docker compose logs --tail=100 users-service
```

## Налаштування та безпека

-   Не зберігайте реальні паролі, JWT secrets та інші секрети у
    відкритому репозиторії.
-   Для локального середовища використовуйте `.env` або локальні user
    secrets, якщо конфігурація застосунку це підтримує.
-   Перед публікацією замініть тестові паролі PostgreSQL і RabbitMQ.
-   Переконайтеся, що рядки підключення в `appsettings.json` не
    перезаписують очікувані змінні середовища Docker.
-   Перевірте, що міграції кожного `DbContext` застосовуються до
    потрібної бази даних.
