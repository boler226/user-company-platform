# Лабораторна №1: бази даних платформи користувачів і компаній

## Як читати цю папку

Це вихідні SQL- та JSON-файли для C#-проєкту [DatabaseSetup](../../DatabaseSetup/README.md).

- `users/` — таблиці користувачів і заявок, процедури та початкові записи.
- `companies/` — таблиці компаній, реквізитів, підрозділів і тегів.
- `notifications/` — правила валідації MongoDB та приклади документів.
- `ERD.md` — діаграми зв'язків між таблицями.
- `01-*` створює структуру, `02-*` додає процедури, `03-*` наповнює даними,
  `03a-*` додає поля наявного API, `04-*` містить ручні перевірки.

Приховані `.venv`, `__pycache__` і `.env`, якщо вони залишилися локально,
походять із попереднього Python-етапу та не використовуються C#-запуском.
`.local-mongo` містить локальні дані попереднього запуску MongoDB, а не вихідний код;
цю папку не слід видаляти, поки відповідний процес MongoDB працює.
Усі ці локальні файли виключено з Git і Docker-контексту.

## Предметна область та межі роботи

Користувачі реєструються на платформі та подають заявки на вступ до компаній.
Адміністратори компаній ведуть довідник компаній, підрозділів і напрямів діяльності,
перевіряють заявки; користувачі отримують сповіщення про події та результати.
Система зберігає історію заявок і доставлення повідомлень.

Тему користувачів і компаній погоджено замість прикладу інтернет-магазину.
PostgreSQL 16 використано як дозволену методичкою альтернативу SQL Server та
як наявну в репозиторії СУБД. `uuid` відповідає GUID, `FOR UPDATE` — блокуванню
рядка через UPDLOCK, `RAISE EXCEPTION` — керованій помилці THROW,
а `bigint version` з тригером — контролю конкурентності замість SQL Server rowversion.
Статуси замовлення адаптовані до заявки на вступ: оплати й відвантаження в цьому домені немає.

Схеми інтегровані в C#-сервіси. Актуальні команди запуску, налаштування
та ручні сценарії наведено в [кореневому README](../../README.md).
Python-розгортання замінене C#-проєктом DatabaseSetup.

## Контексти, власники й агрегати

| Проєкт | База / майбутній сервіс | Сутності й агрегати |
|---|---|---|
| №1, ADO.NET/Dapper | PostgreSQL `lab01_users` / UserService | `users` + `user_profiles`; `membership_applications` + append-only `application_status_history`; `company_directory` — локальна проєкція чужого агрегату |
| №2, EF Core | PostgreSQL `lab01_companies` / CompanyService | `companies` + `company_details` + `departments` + `company_tags`; окремий довідник `tags` |
| №3, MongoDB | `lab01_notifications` / NotificationService | `notifications` із вкладеними об'єктами; `deliveryAttempts` — повна історія; `templates` — самостійний агрегат |

Кожна сутність має одного власника. Один PostgreSQL-сервер обслуговує **дві різні БД**,
а не дві спільні схеми. Між базами немає JOIN, FK, FDW або database links.
Ідентифікатори інших контекстів є логічними посиланнями, перевірка їх існування
в майбутніх сервісах виконується через API/події. Локальний FK заявки до
`company_directory` перевіряє лише локальну проєкцію.

## Політика дублювання

| Поле в копії | Власник / джерело | Політика |
|---|---|---|
| `company_directory.id` | Companies: `companies.id` | Незмінний логічний ID, той самий UUID; міжбазового FK немає |
| `company_directory.name` | Companies: `companies.name` | Seed та оновлення через HTTP API компаній при поданні заявки; повна подієва синхронізація — ЛР №8 |
| `company_directory.source_version` | Companies: `companies.version` | Версія джерела; приймати подію лише з більшою версією, старі/повторні ігнорувати |
| `company_directory.is_deleted` | Companies: `companies.is_deleted` | Подія архівування ставить прапорець, нові заявки забороняються; історію не видаляти |
| `membership_applications.company_id` | Companies: `companies.id`, через локальний довідник | Незмінне посилання на компанію заявки |
| `membership_applications.company_name_snapshot` | Companies: `companies.name`, через локальний довідник | Незмінний знімок на момент подання; перейменування компанії не змінює старі заявки |
| `notifications.recipient.userId` | Users: `users.id` | Незмінне логічне посилання без FK |
| `notifications.recipient.email` | Users: `users.email` | Знімок адреси на момент створення повідомлення; повторні спроби використовують ту саму адресу |
| `notifications.recipient.displayName` | Users: `first_name` + `last_name` | Незмінний знімок для історичного повідомлення |
| `notifications.company.id` | Companies: `companies.id` | Незмінне логічне посилання |
| `notifications.company.name` | Companies: `companies.name` | Незмінний знімок назви при створенні повідомлення |
| `notifications.payload.requestedRole` | Users: `membership_applications.requested_role` | Знімок з події схвалення; не редагується незалежно |
| `recentAttempts[].attemptId/status/occurredAt` | Notifications: `deliveryAttempts._id/status/occurredAt` | Локальна похідна копія останніх трьох спроб; відновлюється з канонічної колекції |

`company_directory.version` — локальна версія рядка, не версія компанії.
Її audit-колонки описують момент внесення проєкції й не дублюють аудит власника.
`templateId` — посилання всередині MongoDB-контексту; текст шаблону не копіюється.
Seed ілюструє історичні знімки, а не відтворює послідовність реальних подій;
зокрема повідомлення про схвалення є автономним прикладом документа.

У ЛР №8 споживач CompanyChanged має атомарно оновлювати проєкцію за `source_version`.
Для `recentAttempts` спочатку записується канонічна спроба, потім кеш останніх трьох;
повторна обробка/відновлення перебудовує кеш, унікальний індекс не дозволяє дубль спроби.
Обробник CompanyChanged ще не реалізовано. Канонічну успішну спробу доставки
та recentAttempts вже записує C# worker; розширення на повторні невдалі спроби — наступний етап.

## Реляційна модель

[ERD обох SQL-баз](ERD.md). Таблиці нормалізовані до 3НФ: профілі й реквізити
відокремлено, теги не повторюються в компаніях, M:N винесено в таблиці зв'язків.
Знімок назви в заявці та локальний довідник — навмисна денормалізація, описана вище.
UUID дозволяє генерувати ідентифікатори в незалежних сервісах без спільного лічильника;
ціна цього вибору — більший розмір ключа, ніж BIGINT.

`user_profiles.user_id` і `company_details.company_id` — одночасно PK та FK, тому
реалізують 1:0..1. M:N `users ↔ company_directory` проходить через заявки з власними
полями ролі/статусу; `companies ↔ tags` — через `company_tags.added_at`.
PK/UNIQUE забезпечують унікальність ID, email, тегів та підрозділу всередині компанії.
CHECK перевіряє статуси, непорожні назви, позитивний бюджет; DEFAULT задає UUID,
час, soft-delete та початкову версію. Профілі, реквізити й зв'язки тегів каскадно
видаляються з коренем; компанії з підрозділами, користувачі із заявками та заявки
з історією захищено RESTRICT. Звичайна бізнес-операція видалення заявки є soft delete.
Історія статусів і спроби доставки append-only, тому не мають UpdatedAt/IsDeleted.

У змінюваних SQL-таблицях є created_at/by, updated_at/by, is_deleted, version.
Тригер зберігає початковий аудит та підвищує версію при кожній зміні.
Аудит `By` ідентифікує логін сервісу; ідентифікатор кінцевого користувача слід додати
при реалізації автентифікованого API. Для компаній майбутній EF Core має позначати
`version` як concurrency token і виконувати `UPDATE ... WHERE id = ... AND version = ...`;
нуль змінених рядків означає конфлікт. Сам тригер без цієї умови конфлікту не відхиляє.
Початкова схема — `01-schema.sql`; подальші зміни потрібно додавати новими
міграціями, а не очікувати, що CREATE TABLE IF NOT EXISTS змінить наявні колонки.

### Індекси та відповідні запити

| Індекс | Призначення |
|---|---|
| Усі PK | Пошук/оновлення за ID; складений PK company_tags — теги компанії |
| UNIQUE users.email / companies.email | Перевірка дубля й точний пошук за email |
| UNIQUE tags.name | Пошук довідникового тегу за назвою |
| UNIQUE departments(company_id, name) | Список/пошук підрозділів компанії, підтримка FK |
| ux_application_current | Одна поточна нескасована заявка користувача до компанії |
| ix_application_user_status | Заявки користувача за статусом, стабільна пагінація; INCLUDE покриває company_id/requested_role |
| ix_application_company | Черга заявок адміністратора компанії |
| ix_history_application | Історія однієї заявки за часом |
| ix_companies_name | Префіксний пошук `lower(name) LIKE 'con%'` серед неархівованих |
| ix_company_tags_tag | Компанії з певним тегом |
| MongoDB `_id` | Ідентифікація документа й повторюваний seed |
| templates(code, channel), UNIQUE | Шаблон події для каналу |
| notifications(recipient.userId, createdAt DESC, _id) | Сторінка вхідних повідомлень користувача |
| notifications(status, scheduledAt), частковий Pending | Черга відкладеного надсилання |
| deliveryAttempts(notificationId, number), UNIQUE | Повна історія та захист від повторної спроби з тим самим номером |

### П'ять процедур

1. `create_application(id, user_id, company_id, role)` — перевірка активних локальних
   користувача/компанії, фіксація назви, початковий статус та історія в одній транзакції.
2. `get_application(id, INOUT result jsonb)` — читання одного неархівованого агрегату.
3. `update_application(id, role, expected_version)` — редагування лише Submitted.
4. `delete_application(id, expected_version)` — soft delete лише Cancelled.
5. `change_application_status(id, status, expected_version)` — блокування FOR UPDATE,
   перевірка версії й допустимого переходу, зміна статусу та запис історії атомарно.

Дозволено `Submitted → AwaitingValidation → Approved → Active` та `Cancelled`
із перших трьох станів. Active/Cancelled — кінцеві. Прямий Submitted → Active та
скасування активної заявки відхиляються SQLSTATE P0001; застаріла версія — 40001,
відсутній/видалений запис — P0002. `CALL` виконується в транзакції PostgreSQL;
процедури не роблять внутрішній COMMIT, тому також працюють усередині транзакції клієнта.
Сервісний логін не має UPDATE таблиць і не може обійти статусну процедуру.

## MongoDB

`notifications` вбудовує recipient, company, payload та масив останніх трьох спроб.
`deliveryAttempts` містить необмежену повну історію й посилається на notificationId;
разом це гібридний підхід. `templateId` посилається на слабко пов'язаний шаблон.
MongoDB не забезпечує FK: майбутній сервіс перевіряє templateId/notificationId.
Приклади демонструють різні поля однієї колекції: readAt проти scheduledAt,
subject проти actions; payload містить вкладені об'єкти та масиви.
JSON Schema перевіряє обов'язкові поля, BSON date, статус, priority 1..5 та
обмеження recentAttempts до трьох елементів, залишаючи додаткові поля дозволеними.
Оновлення сповіщення/шаблону має фільтрувати за `_id, version`, підвищувати version
та updatedAt/by; це забезпечує MongoDB-репозиторій worker.

## Розгортання та перевірка

Використовуйте [кореневий README](../../README.md) та C# DatabaseSetup.
SQL-файли та JSON вбудовано в його вихідний каталог; порядок: schema → procedures →
seed → додаткові поля застосунку → grants; MongoDB: validators → seed → indexes → login.
Скрипти 04-verify.sql залишено для ручного виконання. Автоматичні перевірки після
C#-інтеграції не запускалися за домовленістю з користувачем.

Реєстрація користувачів тепер використовує ту саму таблицю users, що й заявки.
03a-application.sql додає password_hash (BCrypt), role і логічний company_id.
UserService має INSERT/UPDATE лише users, user_profiles, company_directory;
membership_applications та історія змінюються лише процедурами.
CompanyService використовує EF Core, NotificationService — MongoDB.Driver.
company_directory оновлюється при поданні заявки через HTTP API власника за
source_version. Повна подієва синхронізація перейменування/архівування залишається
для наступних робіт. Старі знімки в заявках не змінюються.
Реєстраційне сповіщення може не мати company; його displayName наразі дорівнює
email, оскільки наявна подія UserRegistered містить лише ID, email і дату.
Історія доставки та recentAttempts записуються worker після успішного SMTP.

Довідковий опис вище містить цільову політику для наступних лабораторних;
фактичний інтегрований шлях запуску описаний у кореневому README.
