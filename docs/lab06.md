# Лабораторна № 6. gRPC і Redis

Gateway приймає REST-запити. Aggregator викликає Users, Companies та Notifications через gRPC.
Заявки й сповіщення завантажуються паралельно. Далі Aggregator паралельно завантажує компанії зі сторінки заявок.
Якщо downstream-виклик завершується з помилкою або спливає його 4-секундний deadline, відповідь містить доступні дані та warnings.

Згенеровані сервери й клієнти використовують ті самі контракти з папок Protos у трьох наявних API.
AppHost призначає REST-порт та окремий локальний порт HTTP/2. Service discovery знаходить gRPC
через імена на кшталт http://_grpc.companies-api. Внутрішні порти gRPC доступні на loopback.
HTTP-політики повторів із лабораторної № 5 залишаються для REST. gRPC-клієнти використовують власний deadline.

| Кеш | Ключ | TTL |
|---|---|---|
| Картка компанії | lab06:companies:{revision}:company:{id} | L1 до 15 с, L2 60 с |
| Сторінка каталогу | lab06:companies:{revision}:list:{sha256-фільтра} | L1 до 15 с, L2 45 с |
| Огляд користувача | lab06:overview:{userId}:{page}:{revisions} | Redis 30 с |

Для L1 встановлено 1000 одиниць місткості, по одній на запис, зі sliding TTL 5 с.
Перед читанням L1 сервіс перевіряє в Redis поточну ревізію. Це дає всім реплікам
бачити інвалідацію відразу після запису. Після успішної зміни ревізія оновлюється до повернення
відповіді. Старі ключі стають недоступними й видаляються за TTL. Огляд враховує ревізії
заявок, компаній та сповіщень. Часткові відповіді не записуються в кеш.
Якщо Redis недоступний, читання йде до джерела. Якщо Redis не прийняв інвалідацію після запису,
попередні записи можуть залишитися доступними до закінчення їхнього TTL.

## Запуск і ручна перевірка

Відкрий Docker Desktop і запусти AppHost з кореня репозиторію.

```powershell
dotnet run --project Platform.AppHost/Platform.AppHost.csproj
```

Для першого запуску налаштуй секрети й сертифікат за інструкцією в кореневому README.
Redis використовує volume platform-lab06-redis. Підключення передає Aspire, окремо запускати Redis не потрібно.

1. Отримай JWT способом із README. Виклич GET /api/companies/{id} двічі через Gateway.
   Перша відповідь заповнить кеш, повторна в межах 15 секунд має показати L1 hit і trace без SQL-запиту компанії.
   Почекай 16 секунд після першого запиту й повтори, щоб побачити L2 hit.
2. Виклич GET /api/aggregator/users/10000000-0000-0000-0000-000000000001/overview
   через Gateway на http://localhost:8080. У першому trace мають бути виклики gRPC, у повторному — читання Redis.
3. Онови компанію через PUT з актуальною версією. Наступні GET картки, списку й огляду мають
   прочитати актуальні дані. У логах шукай CompanyUpdated.
4. Зупини notifications-api в Dashboard і зачекай понад 30 секунд або використай іншу сторінку для промаху кешу.
   Aggregator має повернути HTTP 200 із доступними даними та попередженням.
   Повтори виклик і перевір, що часткова відповідь не кешувалася.
5. У Dashboard перевір метрики cache.hits, cache.misses і cache.invalidations
   з Meter Platform.Cache. Відфільтруй логи за X-Correlation-Id і зістав їх з gRPC spans.

Для звіту зроби знімки trace з gRPC, повторного читання картки без SQL та метрики попадань у кеш.
Для порівняння з № 5 виміряй той самий запит і той самий набір даних після прогріву процесів,
але з промахом кешу огляду. Окремо запиши час відповіді з кешу.
